# 报警分析接入最小 AI client

- 目标：把手动“分析报警”真正接上 AI，先打通最小 OpenAI-compatible 链路。
- 改动：
  - 新增 `src/server/alerts/ai-service.ts`。
  - 当前 AI client 会读取项目里的 `aiConfig.baseUrl`、`aiConfig.model`、`aiConfig.apiKey`。
  - 请求走 `POST /chat/completions`，按 OpenAI-compatible 协议发 `system + user` messages。
  - prompt 输入包含：
    - 报警基础信息
    - 本地仓库搜索出来的 1~3 个报警位置候选
    - 每个候选的代码片段
    - 精简后的 `rawAlert`
  - 模型输出被限制成严格 JSON，并用 `zod` 校验：
    - `rootCause`
    - `impact`
    - `codeLocations`
    - `fixSuggestions`
  - `src/server/alerts/repository.ts` 的 `/alerts/:id/analyze` 现在会先找候选位置，再调用 AI，最后写回 `detail.analysis`。
  - `src/components/dashboard/analysis-action.tsx` 现在会检查 AI 配置是否完整；未配置时按钮不可用。
  - `src/components/detail-content/analysis.tsx` 现已展示 `impact`。
- 验证：
  - `./node_modules/.bin/biome check src/server/alerts/ai-service.ts src/server/alerts/repository.ts src/components/dashboard/helpers.tsx src/components/detail-content/analysis.tsx src/components/dashboard/analysis-action.tsx src/localization/i18n.ts`
  - `./node_modules/.bin/tsc --noEmit --pretty false --skipLibCheck`
- 待办：
  - 实测 PackyAPI 下具体模型名和返回格式。
  - 必要时再加 response 解析兜底和 prompt 微调。

# PackyAPI 验证脚本

- 目标：验证 PackyAPI 实际是否兼容当前后端使用的 OpenAI-compatible `chat/completions`。
- 改动：
  - 新增 `scripts/verify-packyapi.ts`。
  - 支持通过环境变量或 CLI 参数传入：
    - `PACKY_API_KEY`
    - `PACKY_MODEL`
    - `PACKY_BASE_URL`
  - 默认 base URL 是 `https://www.packyapi.com/v1`。
  - 会探测：
    - `GET /models`
    - `POST /chat/completions`
    - 可选 `POST /responses`（加 `--responses`）。
  - 输出会隐藏 key，只显示前后 4 位。
- 使用：
  - `PACKY_API_KEY=sk-xxx PACKY_MODEL=model-name npx ts-node scripts/verify-packyapi.ts`
  - `PACKY_API_KEY=sk-xxx PACKY_MODEL=model-name npx ts-node scripts/verify-packyapi.ts --base-url https://codex-api.packycode.com/v1 --responses`
- 验证：

# OpenAI-compatible API 路径说明

- 目标：解释 PackyAPI / OpenAI-compatible 里的 `baseUrl`、`/v1/chat/completions`、`/v1/responses`、`/v1/embeddings` 等路径分别代表什么。
- 结论：
  - `baseUrl` 只是 API 根地址，不是具体功能接口。
  - 真实请求必须是 `baseUrl + endpoint`，例如 `https://www.packyapi.com/v1/chat/completions`。
  - 当前项目报警分析只需要 `/v1/chat/completions`。
  - `/v1/responses` 是 OpenAI 新一代统一生成接口，但 PackyAPI 是否完整支持要以脚本实测为准。
  - `/v1/embeddings` 是把文本转向量，用于语义搜索 / RAG / memory，不用于直接生成答案。
- 待办：
  - 如果后续要做代码库 memory / RAG，再单独验证 PackyAPI 是否支持 embeddings 模型和 `/v1/embeddings`。

# 修复 AI 响应体重复读取

- 目标：修复手动分析时报 `Body is unusable: Body has already been read`，导致详情页不显示 AI 结果的问题。
- 原因：
  - `analyzeAlertWithAi` 里为了调试先执行了 `await response.json()` 打印响应。
  - 后面又执行 `response.json()` 或错误分支 `response.text()`。
  - fetch 的 `Response` body 只能读取一次，所以第二次读取会报错。
- 改动：
  - `src/server/alerts/ai-service.ts` 现在只执行一次 `await response.text()`。
  - 成功和失败都基于同一个 `responseText` 解析，不再重复读取 body。
  - 移除了临时 `console.log`。
  - 补回 `buildChatCompletionUrl`，兼容用户填写 `https://xxx/v1` 或 `https://xxx` 两种 base URL。
  - 顺手格式化了 `src/server/alerts/repository.ts` 的已有格式问题。
- 验证：
  - `./node_modules/.bin/biome check src/server/alerts/ai-service.ts src/server/alerts/repository.ts`
  - `./node_modules/.bin/tsc --noEmit --pretty false --skipLibCheck`
- 待办：重新点“分析报警”验证 detail-content 能显示结果。

# PackyAPI 验证脚本增强

- 目标：排查 `verify-packyapi.ts` 在 `POST /chat/completions` 返回 400 时不够好定位的问题。
- 结论：
  - 脚本本身打的是 `/chat/completions`（复数），不是 `/chat/completion`（单数）。
  - 如果你看到的是单数路径，那就是手动输入或理解时写错了；OpenAI-compatible 常见接口是复数 `completions`。
  - 400 更像是模型名不对、服务不支持某参数，或者该平台只部分兼容 OpenAI 协议。
- 改动：
  - `scripts/verify-packyapi.ts` 现在会输出最终请求 URL。
  - `GET /models` 后会额外检查你传入的模型名是否真的在可用模型列表里。
  - `POST /chat/completions` 的测试请求已收敛成最小 body，不再带 `temperature`，避免因为额外参数触发 400。
- 验证：
  - `./node_modules/.bin/biome check scripts/verify-packyapi.ts`
  - `./node_modules/.bin/tsc --noEmit --pretty false --skipLibCheck --moduleResolution node --module commonjs --target ES2022 --types node scripts/verify-packyapi.ts`
  - `npx ts-node scripts/verify-packyapi.ts --help`
- 待办：
  - 用真实 key 再跑一次，把 `GET /models` 和 `POST /chat/completions` 的输出贴回来看具体 400 原因。
