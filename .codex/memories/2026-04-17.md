# AI 链路与 harness 计划

- 目标：开始打通报警分析的 AI 链路，并明确 harness 的最小开发范围。
- 结论：
  - 下一步确实该进入 AI 部分。
  - 但先不要做“大而全”的通用 harness，先做一个只服务于“报警分析”的最小 harness。
- 计划：
  - 第一步：补一个直接的 AI 调用层，读取项目里的 `baseUrl`、`model`、`apiKey`，只支持 OpenAI-compatible 请求。
  - 第二步：补一个分析上下文层，输入是 alert + 本地 repo path，输出是给模型的上下文包。
  - 第三步：上下文包先只包含：
    - 报警基础信息（title/message/source/rawAlert）
    - 已搜出来的 1~3 个报警位置候选
    - 每个候选文件附近代码片段
  - 第四步：定义一个严格 JSON 输出 schema，让模型只返回：
    - `rootCause`
    - `impact`
    - `codeLocations`
    - `fixSuggestions`
  - 第五步：把现有 `/alerts/:id/analyze` 改成真实 AI 分析，并把结果持久化到 `detail.analysis`。
  - 第六步：前端先复用现有详情区，不做复杂流式 UI。
- 待办：
  - 后续再把这个最小 harness 扩成“生成 patch / 提 PR”的第二阶段。

# PackyAPI 可接入性确认

- 目标：确认 PackyAPI 是否只能用于 CLI，还是也能给当前桌面应用后端直接调 API。
- 结论：
  - 可以接，不是只能给 CLI 脚手架用。
  - 官方文档明确写了“兼容 OpenAI 接口协议”，并说明可以接入第三方平台。
  - `Codex` 分组在官方“令牌分组介绍”里也明确标注为“支持接入第三方”。
- 接入建议：
  - 对我们这个项目，先不要走 `responses`，优先走官方文档明确写出来的 `POST /v1/chat/completions`。
  - 如果你是普通 PackyAPI 令牌，优先用 `https://www.packyapi.com/v1`。
  - 如果你用的是 Packy 的 Codex 包月文档场景，官方文档提到 base URL 可能要换成 `https://codex-api.packycode.com/v1`。
  - 模型名按你控制台实际可用模型填，不要死写文档示例。
- 风险提示：
  - 官方文档写了：如果接入 New API 等第三方平台，建议先联系客服报备，避免被误判为滥用。
  - 官方 CLI 文档大量展示的是 `wire_api = "responses"`，但第三方接入章节明确写的是 `/v1/chat/completions`；所以对我们自研后端，第一版用 `chat/completions` 最稳。
- 待办：
  - 下一步在后端落一个最小 AI client，先按 OpenAI-compatible `chat/completions` 接 PackyAPI。
